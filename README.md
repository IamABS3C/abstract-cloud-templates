# Abstract cloud templates

Deployment templates for sending AWS, Azure and Google Cloud logs to Abstract Security.

## Azure

| Template | Role | Summary |
|---|---|---|
| [App registrations, by Logic App](templates/azure/azure-access-app-registration-logic-app/README.md) | access | The recommended path for per-subscription app registrations: one Logic App in one resource group, running as one pre-consented identity, calls Microsoft Graph directly when a subscription is created or tagged. Same outcome as the policy path with one identity to audit, no per-subscription compute and a single run history. |
| [App registrations, by policy](templates/azure/azure-access-app-registration-management-group-policy/README.md) | access | Azure Policy cannot create Entra objects, so this policy deploys a deployment script that runs as a pre-consented managed identity and calls Microsoft Graph. Each in-scope subscription gets its own app, credential and subscription-scoped RBAC. The event-driven automation path is safer for most customers. |
| [Key Vault secrets reader](templates/azure/azure-access-key-vault-secrets-reader/README.md) | access | A small helper that grants one role to one principal on an existing Key Vault. The Sentinel destination templates call it as a module to give their identities Key Vault Secrets Officer or Secrets User on the vault that holds the client secret. |
| [Event Hub destination](templates/azure/azure-destination-event-hub/README.md) | destination | Provisions the Azure side of the Abstract Azure EventHub Destination: an Event Hubs namespace and one hub that Abstract delivers processed events into, with a Send-only SAS rule or an RBAC grant. Safe Mode keeps public access on so Abstract can always reach the hub during onboarding. |
| [Sentinel destination](templates/azure/azure-destination-sentinel/README.md) | destination | Prepares Azure for the Abstract Azure Sentinel Destination: a Data Collection Endpoint, a Data Collection Rule and the custom Abstract table, in a new or existing workspace, with Monitoring Metrics Publisher on the DCR for the app you created. Recommended for production; no privileged identity is involved. |
| [Sentinel destination, app by Graph](templates/azure/azure-destination-sentinel-app-by-graph/README.md) | destination | Creates the Entra app registration and service principal as the person deploying, using the Microsoft Graph Bicep extension, then calls the standard destination template. No managed identity has to exist first; optional secret automation adds one that owns only this app. CLI only: needs the Microsoft Graph Bicep extension (Azure CLI or PowerShell). |
| [Sentinel destination, app by script](templates/azure/azure-destination-sentinel-app-by-script/README.md) | destination | The portal-wizard variant of the Sentinel destination: a deployment script creates the Entra app registration and, with Key Vault, its client secret, then the template builds the same ingestion stack. It runs as a tier-0 managed identity you create beforehand, so it suits portal-only teams and labs. |
| [Sentinel content pack](templates/azure/azure-destination-sentinel-content-pack/README.md) | destination | A self-contained approximation of the Abstract Microsoft Sentinel solution that installs connector tiles, an ASIM parser function, analytics and automation rules, hunting queries, workbooks and playbooks into an existing Sentinel workspace. Sufficient for a lab or private install; not a substitute for the certified Content Hub package. |
| [Event Hub source](templates/azure/azure-foundation-event-hub/README.md) | foundation | Azure Monitor cannot send diagnostic data directly to a third party, so every Azure onboarding starts here: an Event Hubs namespace with one hub per log source, a consumer group Abstract reads from, and a checkpoint storage account. Deploy it first; the Activity Log, Entra ID and policy templates consume its outputs. |
| [Pipeline health alerts](templates/azure/azure-monitoring-event-hub-health-alerts/README.md) | monitoring | Event Hubs publishes no consumer-lag metric, so when the Abstract consumer stalls, incoming traffic keeps arriving, nothing errors, and retention quietly expires the backlog. These alert rules watch for outgoing traffic collapsing while incoming continues, plus the producer-side and capacity failures. |
| [Activity Log, one subscription](templates/azure/azure-source-activity-log-subscription/README.md) | source | The pilot path: streams one subscription's Activity Log, every ARM create, update and delete and every RBAC change, to the Abstract Event Hub. Use it to prove the pipeline on one subscription, then move to the management-group policy for the estate. |
| [Azure logs, every subscription](templates/azure/azure-source-all-logs-management-group-policy/README.md) | source | Assign once at a management group and every subscription in it, today's and every one added later, streams to the Abstract Event Hub and drifts back into compliance if a setting is removed. Covers the Activity Log, resource logs, Azure SQL auditing and Defender for Cloud export, each a separate Azure mechanism. |
| [Entra ID logs](templates/azure/azure-source-entra-id-logs-tenant/README.md) | source | Entra ID activity logs are a single tenant-level diagnostic setting on the microsoft.aadiam provider, not Azure Monitor resource logs. Azure Policy cannot manage them, and a portal deployment at tenant scope is still pending proof, so for now one CLI command onboards identity telemetry for the whole organisation. |

## AWS

| Template | Role | Summary |
|---|---|---|
| [Read role, existing bucket](templates/aws/aws-access-read-role-existing-bucket-and-queue/README.md) | access | Creates only the least-privilege IAM role Abstract assumes, with an External ID, to read log objects from an existing bucket and consume notifications from an existing queue. It is the role-based option the Abstract S3 + SQS integration wizards refer to as Generate IAM Role Permissions. |
| [Log delivery lookup helper](templates/aws/aws-foundation-log-delivery-helper/README.md) | foundation | A Lambda-backed custom resource that does at deploy time what plain CloudFormation cannot: resolve a KMS alias, a queue name, a stream or a web ACL to its ARN, validate a bucket, check a log group, and optionally switch on S3 server access logging or load balancer access logs. Other stacks call it through its exported ServiceToken. |
| [CloudFront logs](templates/aws/aws-source-cloudfront-logs-s3-sqs/README.md) | source | Creates the hardened S3 bucket CloudFront standard logging writes to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [CloudTrail logs](templates/aws/aws-source-cloudtrail-s3-sqs/README.md) | source | Creates a CloudTrail trail, its hardened S3 bucket, the SNS topic and SQS queue the trail notifies, and the cross-account role Abstract assumes to read them. |
| [CloudWatch Logs by API](templates/aws/aws-source-cloudwatch-logs-api/README.md) | source | CloudWatch Logs is an API-poll source with no bucket or queue: Abstract reads log events directly. This template creates only the cross-account identity Abstract uses, scoped to one log group or to every log group in the account and region. |
| [Queues for an existing bucket](templates/aws/aws-source-existing-bucket-queues/README.md) | source | A Terraform or OpenTofu module for a security bucket that holds several log sources under different key prefixes. Because an Abstract S3 + SQS configuration is scoped by its queue alone, the module builds one SQS queue per source and one routing layer in front of them: a direct bucket notification, SNS fan-out, or EventBridge. |
| [Any logs in an S3 bucket](templates/aws/aws-source-generic-s3-sqs/README.md) | source | Creates a hardened S3 bucket any log shipper can write to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [Kinesis data stream](templates/aws/aws-source-kinesis-stream/README.md) | source | Kinesis is an API-poll source: Abstract reads records directly from a stream. This template creates the cross-account identity Abstract uses, scoped to one stream or all streams, and can optionally create the stream itself. |
| [Load balancer access logs](templates/aws/aws-source-load-balancer-logs-s3-sqs/README.md) | source | Creates the hardened S3 bucket an Application, Network or Classic Load Balancer writes access logs to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [Several sources, one stack](templates/aws/aws-source-multiple-sources-one-bucket/README.md) | source | A master stack nests the per-source child templates, so one deploy provisions any combination of CloudTrail, CloudFront, load balancer, Route 53 Resolver, S3 access, VPC Flow, WAF, CloudWatch Logs, Kinesis and Security Lake sources. The Abstract principal, External ID, encryption and alarm settings are entered once and flow down to every enabled child. |
| [Route 53 Resolver query logs](templates/aws/aws-source-route53-resolver-logs-s3-sqs/README.md) | source | Creates a Route 53 Resolver query-logging configuration for a list of VPCs, its hardened S3 bucket, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [S3 server access logs](templates/aws/aws-source-s3-access-logs-s3-sqs/README.md) | source | Creates the hardened destination bucket for S3 server access logging, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [One source, every account](templates/aws/aws-source-s3-sqs-organization-stackset/README.md) | source | A wrapper around CloudFormation StackSets, service-managed for AWS Organizations, that rolls one Abstract template across every account in an organizational unit and a list of regions. With auto-deployment on, accounts added to the OU later receive the stack too. |
| [Security Lake subscriber](templates/aws/aws-source-security-lake/README.md) | source | Registers Abstract as a Security Lake subscriber with S3 data access and an SQS notification, so Abstract is notified of and reads the normalized OCSF objects Security Lake collects. Use it when WAF or other logs are centralised in Security Lake rather than a per-service bucket. |
| [VPC Flow Logs](templates/aws/aws-source-vpc-flow-logs-s3-sqs/README.md) | source | Creates a VPC flow log on one VPC, subnet or network interface, its hardened S3 bucket, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [WAF logs](templates/aws/aws-source-waf-logs-s3-sqs/README.md) | source | Turns on logging for one WAF web ACL into a hardened S3 bucket, with the SQS queue S3 notifies and the cross-account role Abstract assumes to read them. |

## Google Cloud

| Template | Role | Summary |
|---|---|---|
| [Log archive bucket](templates/gcp/gcp-archive-log-bucket/README.md) | archive | A second organization sink writing to a Cloud Storage bucket for evidence and backfill, because a sink has exactly one destination. It is not the detection path: storage batches, so latency is minutes to hours. |
| [Data Access audit logging](templates/gcp/gcp-foundation-data-access-audit-logs/README.md) | foundation | Admin Activity audit logs are always on; Data Access logs are off by default, and until they are on a sink filter referencing data_access matches nothing. This deployment enables the chosen Data Access log types in separate state from the log-export pipeline. |
| [Logging project](templates/gcp/gcp-foundation-logging-project/README.md) | foundation | Optional: enables the APIs the pipeline needs on an existing project, or creates a dedicated logging project with a billing account. Most customers already have a security or logging project and can skip it. |
| [Pipeline health alerts](templates/gcp/gcp-monitoring-pipeline-health-alerts/README.md) | monitoring | A stalled consumer, a missing IAM grant and a deleted sink all look the same from outside: everything is green and there is no data. These Cloud Monitoring alert policies catch sink export failures, an unconsumed subscription, a feed that went dark and a receiving dead-letter topic. |
| [Asset and IAM changes](templates/gcp/gcp-source-asset-and-iam-changes/README.md) | source | Cloud Asset Inventory publishes to Pub/Sub through its own feed, which no log sink can carry. It records what an IAM policy now is and what it was before, the diff a detection wants, alongside the audit log of who called which API. |
| [Audit logs, one folder](templates/gcp/gcp-source-audit-logs-folder/README.md) | source | The same aggregated sink one ring in: every project in a folder and its sub-folders, current and future. Use it when organization-scope IAM has not been granted yet, knowing that any project outside the folder is silently missed. |
| [Audit logs, whole organization](templates/gcp/gcp-source-audit-logs-organization/README.md) | source | One aggregated Cloud Logging sink at organization scope routes audit and platform logs from every project into one Pub/Sub topic for Abstract. Projects created later are covered automatically, because the sink's scope is containment rather than a list. |
| [Audit logs, one project](templates/gcp/gcp-source-audit-logs-project/README.md) | source | A project-scope sink that proves the whole pipeline end to end before organization-scope IAM is requested. It does not cover future or other projects; replace it with the organization sink once the pilot is proven. |
| [Billing account audit logs](templates/gcp/gcp-source-billing-account-logs/README.md) | source | A Cloud Logging sink on the billing account, which sits outside the organization hierarchy, so no organization sink sees it. It routes the billing account's Admin Activity audit logs (IAM changes, project link and unlink, account changes) to Pub/Sub for Abstract. It is not a cost export. |
| [Logs in a Cloud Storage bucket](templates/gcp/gcp-source-cloud-storage-bucket-logs/README.md) | source | For logs that are already objects in a bucket, such as a vendor export or an archive being backfilled. The bucket emits an object-created notification to Pub/Sub and Abstract fetches the object; the notification is a pointer, not the data. |
| [Google Workspace logs](templates/gcp/gcp-source-google-workspace-logs/README.md) | source | A separate pipeline: Abstract's Google Workspace integration reads Workspace audit data from the Admin SDK Reports API, so no Cloud Logging sink or Pub/Sub topic is involved. Terraform creates the service account; a Workspace super admin then grants domain-wide delegation by hand. |
| [Network threat logs](templates/gcp/gcp-source-network-threat-logs/README.md) | source | Routes firewall rule, Cloud DNS query, load balancer (Cloud Armor) and Cloud IDS threat logs to a Pub/Sub topic for Abstract. Abstract's managed GCP parser does not yet store these logs: it keeps only Cloud Audit Log records, and these are not. |
| [Security Command Center findings](templates/gcp/gcp-source-security-command-center-findings/README.md) | source | Security Command Center does not flow through the Log Router; it publishes to Pub/Sub through its own notification config, so no sink will ever collect it. This deployment creates that config and a dedicated topic and subscription, reusing Abstract's existing service account. |
