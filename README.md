# Abstract cloud templates

Deployment templates for sending AWS, Azure and Google Cloud logs to Abstract Security.

## Azure

**Start here: [the setup guide](docs/azure/GUIDE.md).** A few questions lead to one plan, in order, from checking what you have to cleaning it up.

| Template | Role | Summary |
|---|---|---|
| [Abstract access to new subscriptions: app registrations by Logic App](templates/azure/azure-access-app-registration-logic-app/README.md) | access | The recommended path for per-subscription app registrations: one Logic App in one resource group, running as one pre-consented identity, calls Microsoft Graph directly when a subscription is created or tagged. Same outcome as the policy path with one identity to audit, no per-subscription compute and a single run history. |
| [Abstract access to every subscription: app registrations by Policy](templates/azure/azure-access-app-registration-management-group-policy/README.md) | access | Azure Policy cannot create Entra objects, so this policy deploys a deployment script that runs as a pre-consented managed identity and calls Microsoft Graph. Each in-scope subscription gets its own app, credential and subscription-scoped RBAC. The event-driven automation path is safer for most customers. |
| [Read access to a Key Vault: one role assignment](templates/azure/azure-access-key-vault-secrets-reader/README.md) | access | A small helper that grants one role to one principal on an existing Key Vault. The Sentinel destination templates call it as a module to give their identities Key Vault Secrets Officer or Secrets User on the vault that holds the client secret. |
| [Abstract to your Event Hub: namespace and hub](templates/azure/azure-destination-event-hub/README.md) | destination | Provisions the Azure side of the Abstract Azure EventHub Destination: an Event Hubs namespace and one hub that Abstract delivers processed events into, with a Send-only SAS rule or an RBAC grant. Safe Mode keeps public access on so Abstract can always reach the hub during onboarding. |
| [Abstract to Microsoft Sentinel: with your app registration](templates/azure/azure-destination-sentinel/README.md) | destination | Prepares Azure for the Abstract Azure Sentinel Destination: a Data Collection Endpoint, a Data Collection Rule and the custom Abstract table, in a new or existing workspace, with Monitoring Metrics Publisher on the DCR for the app you created. Recommended for production; no privileged identity is involved. |
| [Abstract to Sentinel: app registration created by Graph](templates/azure/azure-destination-sentinel-app-by-graph/README.md) | destination | Creates the Entra app registration and service principal as the person deploying, using the Microsoft Graph Bicep extension, then calls the standard destination template. No managed identity has to exist first; optional secret automation adds one that owns only this app. CLI only: needs the Microsoft Graph Bicep extension (Azure CLI or PowerShell). |
| [Abstract to Sentinel: app registration created by script](templates/azure/azure-destination-sentinel-app-by-script/README.md) | destination | The portal-wizard variant of the Sentinel destination: a deployment script creates the Entra app registration and, with Key Vault, its client secret, then the template builds the same ingestion stack. It runs as a tier-0 managed identity you create beforehand, so it suits portal-only teams and labs. |
| [Sentinel content for Abstract data: rules and workbooks](templates/azure/azure-destination-sentinel-content-pack/README.md) | destination | A self-contained approximation of the Abstract Microsoft Sentinel solution that installs connector tiles, an ASIM parser function, analytics and automation rules, hunting queries, workbooks and playbooks into an existing Sentinel workspace. Sufficient for a lab or private install; not a substitute for the certified Content Hub package. |
| [Azure first step: Event Hub that receives all logs](templates/azure/azure-foundation-event-hub/README.md) | foundation | Azure Monitor cannot send diagnostic data directly to a third party, so every Azure onboarding starts here: an Event Hubs namespace with one hub per log source, a consumer group Abstract reads from, and a checkpoint storage account. Deploy it first; the Activity Log, Entra ID and policy templates consume its outputs. |
| [Azure alerts when the Abstract feed stalls](templates/azure/azure-monitoring-event-hub-health-alerts/README.md) | monitoring | Event Hubs publishes no consumer-lag metric, so when the Abstract consumer stalls, incoming traffic keeps arriving, nothing errors, and retention quietly expires the backlog. These alert rules watch for outgoing traffic collapsing while incoming continues, plus the producer-side and capacity failures. |
| [Activity Log to Abstract: one subscription](templates/azure/azure-source-activity-log-subscription/README.md) | source | The pilot path: streams one subscription's Activity Log, every ARM create, update and delete and every RBAC change, to the Abstract Event Hub. Use it to prove the pipeline on one subscription, then move to the management-group policy for the estate. |
| [All Azure logs to Abstract: every subscription by Policy](templates/azure/azure-source-all-logs-management-group-policy/README.md) | source | Assign once at a management group and every subscription in it, today's and every one added later, streams to the Abstract Event Hub and drifts back into compliance if a setting is removed. Covers the Activity Log, resource logs, Azure SQL auditing and Defender for Cloud export, each a separate Azure mechanism. |
| [Entra ID sign-in and audit logs to Abstract](templates/azure/azure-source-entra-id-logs-tenant/README.md) | source | Entra ID activity logs are a single tenant-level diagnostic setting on the microsoft.aadiam provider, not Azure Monitor resource logs. Azure Policy cannot manage them, and a portal deployment at tenant scope is still pending proof, so for now one CLI command onboards identity telemetry for the whole organisation. |

## AWS

**Start here: [the setup guide](docs/aws/GUIDE.md).** A few questions lead to one plan, in order, from checking what you have to cleaning it up.

| Template | Role | Summary |
|---|---|---|
| [CloudWatch metrics to Abstract: read-only role](templates/aws/aws-access-cloudwatch-metrics-role/README.md) | access | Creates only the read-only IAM role Abstract assumes, with an External ID, to read CloudWatch metrics and describe RDS instances for the AWS CloudWatch Metrics integration. There is no bucket and no queue. Deployed in a test account on 2026-10-07. The role was assumed with its External ID. |
| [Existing S3 logs to Abstract: read-only access role](templates/aws/aws-access-read-role-existing-bucket-and-queue/README.md) | access | Creates only the least-privilege IAM role Abstract assumes, with an External ID, to read log objects from an existing bucket and consume notifications from an existing queue. It is the role-based option the Abstract S3 + SQS integration wizards refer to as Generate IAM Role Permissions. |
| [Abstract to your S3 bucket: write-only export role](templates/aws/aws-destination-s3-export-role/README.md) | destination | Creates only the IAM role Abstract assumes, with an External ID, to write exported events into one existing S3 bucket under one prefix, for the S3 Export destination. The role cannot read your objects. Deployed in a test account on 2026-10-07. The role was assumed with its External ID. |
| [AWS helper: look up resources and switch on logging](templates/aws/aws-foundation-log-delivery-helper/README.md) | foundation | A Lambda-backed custom resource that does at deploy time what plain CloudFormation cannot: resolve a KMS alias, a queue name, a stream or a web ACL to its ARN, validate a bucket, check a log group, and optionally switch on S3 server access logging or load balancer access logs. Other stacks call it through its exported ServiceToken. |
| [Dead-letter queue alarms: email when Abstract cannot read](templates/aws/aws-monitoring-sqs-dead-letter-alarms/README.md) | monitoring | Creates a CloudWatch alarm on each of up to ten existing SQS dead-letter queues and one SNS topic they publish to, with an optional email subscription, so a message Abstract could not process is seen within minutes. It creates no queue and changes none. Deployed in a test account on 2026-10-07. A message on the dead-letter queue put the alarm in ALARM. |
| [CloudFront logs to Abstract: new bucket and queue](templates/aws/aws-source-cloudfront-logs-s3-sqs/README.md) | source | Creates the hardened S3 bucket CloudFront standard logging writes to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [CloudTrail to Abstract: new trail, bucket and queue](templates/aws/aws-source-cloudtrail-s3-sqs/README.md) | source | Creates a CloudTrail trail, its hardened S3 bucket, the SNS topic and SQS queue the trail notifies, and the cross-account role Abstract assumes to read them. |
| [CloudWatch Logs to Abstract: direct API read](templates/aws/aws-source-cloudwatch-logs-api/README.md) | source | CloudWatch Logs is an API-poll source with no bucket or queue: Abstract reads log events directly. This template creates only the cross-account identity Abstract uses, scoped to one log group or to every log group in the account and region. |
| [AWS Config history to Abstract: new bucket and queue](templates/aws/aws-source-config-history-s3-sqs/README.md) | source | Creates a hardened bucket AWS Config may deliver to, the SQS queue it notifies for each configuration history file, the role Abstract assumes to read them and, only when you opt in, this Region's AWS Config delivery channel. Abstract reads it with the generic S3 source and a custom parser. Deployed in a test account on 2026-10-07. A Config history file reached the queue, and the role was assumed with its External ID. |
| [EKS control-plane logs to Abstract: Firehose to S3](templates/aws/aws-source-eks-control-plane-logs/README.md) | source | Subscribes your EKS cluster's control-plane log group to a Firehose delivery stream that decompresses the records and writes one log line per line to a new hardened bucket, plus the SQS queue the bucket notifies and the role Abstract assumes to read them. For clusters too busy for the CloudWatch Logs API read. Not yet deployed by Abstract; canary pending. |
| [Shared S3 bucket to Abstract: one queue per source](templates/aws/aws-source-existing-bucket-queues/README.md) | source | A Terraform or OpenTofu module for a security bucket that holds several log sources under different key prefixes. Because an Abstract S3 + SQS configuration is scoped by its queue alone, the module builds one SQS queue per source and one routing layer in front of them: a direct bucket notification, SNS fan-out, or EventBridge. |
| [Any S3 logs to Abstract: new bucket and queue](templates/aws/aws-source-generic-s3-sqs/README.md) | source | Creates a hardened S3 bucket any log shipper can write to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [GuardDuty findings to Abstract: new key, bucket and queue](templates/aws/aws-source-guardduty-findings-s3-sqs/README.md) | source | Creates the customer managed KMS key GuardDuty's S3 export requires, a hardened findings bucket, a publishing destination on your existing GuardDuty detector, the SQS queue the bucket notifies and the role Abstract assumes to read them. Not yet deployed by Abstract; canary pending. |
| [Kinesis stream to Abstract: direct stream read](templates/aws/aws-source-kinesis-stream/README.md) | source | Kinesis is an API-poll source: Abstract reads records directly from a stream. This template creates the cross-account identity Abstract uses, scoped to one stream or all streams, and can optionally create the stream itself. |
| [Load balancer logs to Abstract: new bucket and queue](templates/aws/aws-source-load-balancer-logs-s3-sqs/README.md) | source | Creates the hardened S3 bucket an Application, Network or Classic Load Balancer writes access logs to, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [Several AWS sources to Abstract in one deploy](templates/aws/aws-source-multiple-sources-one-bucket/README.md) | source | A master stack nests the per-source child templates, so one deploy provisions any combination of CloudTrail, CloudFront, load balancer, Route 53 Resolver, S3 access, VPC Flow, WAF, CloudWatch Logs, Kinesis and Security Lake sources. The Abstract principal, External ID, encryption and alarm settings are entered once and flow down to every enabled child. |
| [Network Firewall logs to Abstract: bucket and three queues](templates/aws/aws-source-network-firewall-logs-s3-sqs/README.md) | source | Creates a hardened log bucket, turns on S3 logging for your existing AWS Network Firewall (alert logs always, flow and TLS logs by choice, each under its own prefix), one SQS queue per log type and the role Abstract assumes to read them. Each log type is its own shape and becomes its own Abstract configuration. Not yet deployed by Abstract; canary pending. |
| [Route 53 DNS logs to Abstract: new bucket and queue](templates/aws/aws-source-route53-resolver-logs-s3-sqs/README.md) | source | Creates a Route 53 Resolver query-logging configuration for a list of VPCs, its hardened S3 bucket, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [S3 access logs to Abstract: new bucket and queue](templates/aws/aws-source-s3-access-logs-s3-sqs/README.md) | source | Creates the hardened destination bucket for S3 server access logging, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [One AWS source in every account: organization StackSet](templates/aws/aws-source-s3-sqs-organization-stackset/README.md) | source | A wrapper around CloudFormation StackSets, service-managed for AWS Organizations, that rolls one Abstract template across every account in an organizational unit and a list of regions. With auto-deployment on, accounts added to the OU later receive the stack too. |
| [Security Hub findings to Abstract: EventBridge and Firehose](templates/aws/aws-source-security-hub-findings-firehose/README.md) | source | Creates an EventBridge rule for Security Hub's finding events, a Firehose delivery stream that writes them one per line to a new hardened bucket, the SQS queue the bucket notifies and the role Abstract assumes to read them. Security Hub has no S3 export of its own. Deployed in a test account on 2026-10-07. A record put to Firehose landed in the bucket and reached the queue in about five minutes, and the role was assumed with its External ID. |
| [Security Lake to Abstract: subscriber and SQS notification](templates/aws/aws-source-security-lake/README.md) | source | Registers Abstract as a Security Lake subscriber with S3 data access and an SQS notification, so Abstract is notified of and reads the normalized OCSF objects Security Lake collects. Use it when WAF or other logs are centralised in Security Lake rather than a per-service bucket. |
| [VPC Flow Logs to Abstract: new bucket and queue](templates/aws/aws-source-vpc-flow-logs-s3-sqs/README.md) | source | Creates a VPC flow log on one VPC, subnet or network interface, its hardened S3 bucket, the SQS queue S3 notifies, and the cross-account role Abstract assumes to read them. |
| [WAF logs to Abstract: new bucket and queue](templates/aws/aws-source-waf-logs-s3-sqs/README.md) | source | Turns on logging for one WAF web ACL into a hardened S3 bucket, with the SQS queue S3 notifies and the cross-account role Abstract assumes to read them. |

## Google Cloud

**Start here: [the setup guide](docs/gcp/GUIDE.md).** A few questions lead to one plan, in order, from checking what you have to cleaning it up.

| Template | Role | Summary |
|---|---|---|
| [Archive Google Cloud logs to Cloud Storage: second sink](templates/gcp/gcp-archive-log-bucket/README.md) | archive | A second organization sink writing to a Cloud Storage bucket for evidence and backfill, because a sink has exactly one destination. It is not the detection path: storage batches, so latency is minutes to hours. |
| [Turn on Data Access audit logs: organization, folder or project](templates/gcp/gcp-foundation-data-access-audit-logs/README.md) | foundation | Admin Activity audit logs are always on; Data Access logs are off by default, and until they are on a sink filter referencing data_access matches nothing. This deployment enables the chosen Data Access log types in separate state from the log-export pipeline. |
| [Google Cloud first step: logging project and APIs](templates/gcp/gcp-foundation-logging-project/README.md) | foundation | Optional: enables the APIs the pipeline needs on an existing project, or creates a dedicated logging project with a billing account. Most customers already have a security or logging project and can skip it. |
| [Google Cloud alerts when the Abstract feed stalls](templates/gcp/gcp-monitoring-pipeline-health-alerts/README.md) | monitoring | A stalled consumer, a missing IAM grant and a deleted sink all look the same from outside: everything is green and there is no data. These Cloud Monitoring alert policies catch sink export failures, an unconsumed subscription, a feed that went dark and a receiving dead-letter topic. |
| [Asset and IAM changes to Abstract: asset feed](templates/gcp/gcp-source-asset-and-iam-changes/README.md) | source | Cloud Asset Inventory publishes to Pub/Sub through its own feed, which no log sink can carry. It records what an IAM policy now is and what it was before, the diff a detection wants, alongside the audit log of who called which API. |
| [One folder's audit logs to Abstract: folder sink](templates/gcp/gcp-source-audit-logs-folder/README.md) | source | The same aggregated sink one ring in: every project in a folder and its sub-folders, current and future. Use it when organization-scope IAM has not been granted yet, knowing that any project outside the folder is silently missed. |
| [All Google Cloud audit logs to Abstract: organization sink](templates/gcp/gcp-source-audit-logs-organization/README.md) | source | One aggregated Cloud Logging sink at organization scope routes audit and platform logs from every project into one Pub/Sub topic for Abstract. Projects created later are covered automatically, because the sink's scope is containment rather than a list. |
| [One project's audit logs to Abstract: project sink](templates/gcp/gcp-source-audit-logs-project/README.md) | source | A project-scope sink that proves the whole pipeline end to end before organization-scope IAM is requested. It does not cover future or other projects; replace it with the organization sink once the pilot is proven. |
| [Billing account audit logs to Abstract: billing sink](templates/gcp/gcp-source-billing-account-logs/README.md) | source | A Cloud Logging sink on the billing account, which sits outside the organization hierarchy, so no organization sink sees it. It routes the billing account's Admin Activity audit logs (IAM changes, project link and unlink, account changes) to Pub/Sub for Abstract. It is not a cost export. |
| [Cloud Storage bucket logs to Abstract: object notifications](templates/gcp/gcp-source-cloud-storage-bucket-logs/README.md) | source | For logs that are already objects in a bucket, such as a vendor export or an archive being backfilled. The bucket emits an object-created notification to Pub/Sub and Abstract fetches the object; the notification is a pointer, not the data. |
| [Google Workspace audit logs to Abstract: Reports API](templates/gcp/gcp-source-google-workspace-logs/README.md) | source | A separate pipeline: Abstract's Google Workspace integration reads Workspace audit data from the Admin SDK Reports API, so no Cloud Logging sink or Pub/Sub topic is involved. Terraform creates the service account; a Workspace super admin then grants domain-wide delegation by hand. |
| [Firewall, DNS and IDS logs to Abstract: filtered sink](templates/gcp/gcp-source-network-threat-logs/README.md) | source | Routes firewall rule, Cloud DNS query, load balancer (Cloud Armor) and Cloud IDS threat logs to a Pub/Sub topic for Abstract. Abstract's managed GCP parser does not yet store these logs: it keeps only Cloud Audit Log records, and these are not. |
| [Security Command Center findings to Abstract: notification feed](templates/gcp/gcp-source-security-command-center-findings/README.md) | source | Security Command Center does not flow through the Log Router; it publishes to Pub/Sub through its own notification config, so no sink will ever collect it. This deployment creates that config and a dedicated topic and subscription, reusing Abstract's existing service account. |
